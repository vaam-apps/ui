# Theming and tokens

This library is **Material 3 Expressive, and only that.** Every colour is an
M3 colour role generated from one seed; every corner is a step of M3's corner
scale; every text step is an M3 type role; everything that moves is one of M3
Expressive's springs. All of it is a custom property declared in
`src/styles/theme.css`, and the ones components use are re-exposed as Tailwind
utilities through `@theme inline`. Component code writes `bg-surface-3`,
never `bg-[var(--surface-3)]`.

## Where the colours come from

`scripts/generate-md3-colors.ts` builds the M3 Expressive scheme —
`Variant.EXPRESSIVE`, colour spec 2025, contrast level 0 — from the seed
**`#4f46e5`** with `@material/material-color-utilities` (a devDependency:
consumers receive static CSS), and writes every role into `theme.css` as
`--md-sys-color-<role>`, for dark and for light, between `<md3:generated>`
markers. Run `pnpm generate:colors` after changing the generator; never edit
the generated regions by hand — `hct-neutrals.test.ts` re-runs the generator
and fails on a single differing byte.

Reading a role is reading a custom property:

```css
.callout {
  background: var(--md-sys-color-primary-container);
  color: var(--md-sys-color-on-primary-container);
}
```

Everything else is a **mapping onto** those roles, written by hand beside its
reason: daisyUI's theme tokens (`--color-primary` is `primary`,
`--color-base-100/200/300` are `surface`, `surface-container-low` and
`surface-container`), and this library's own names (`--surface-3`, the
`--edge` ladder, the text tiers, `--ring`). A consumer who overrides a role
re-themes everything that reads it.

**Why indigo and not the house teal.** M3 Expressive's `primary` sits in the
same tone band as the status foregrounds, so only hue and chroma tell a
primary-coloured control from a state. Measured with CIEDE2000, a teal
seed's light `primary` sits **5.5** from `progress` and **9.4** from
`success` — closer than two status hues are allowed to sit to each other
(13). The indigo's nearest status hue is `neutral`, 13.2 away in dark and
14.7 in light. `hct-neutrals.test.ts` pins both halves.

**Only `primary` is chrome.** Expressive rotates `secondary` and `tertiary`
around the wheel — at this seed into the olive band beside `success` — so
where M3 draws a selected row, an active indicator or a focus ring in
`secondary-container` or `tertiary-container`, components here use
`primary-container` or `primary`. The roles are all still there for a
consumer whose screen has no status on it.

That indirection is worth understanding before you use it, because it has a
sharp edge: **Tailwind generates nothing for a token it does not know about,
and says nothing about it.** A class written against an unregistered token
produces a transparent surface, not an error. That has happened here twice —
once when `bg-surface-1` and `bg-surface-2` were used across dozens of files
without ever being registered (confirmed live as `rgba(0,0,0,0)` on a real
render, easy to miss because a transparent panel over a near-black page still
reads as dark enough), and once when `--state-warning-*` was referenced by
`StateChip` and `InlineBanner` from the day both shipped without ever being
declared. `src/lib/theme-tokens.test.ts` now scans the components for
`bg-`/`text-`/`border-` tokens this stylesheet owns and fails the build on a
third occurrence.

Everything below exists in **both** themes, and the swatches show both side by
side rather than following the theme toolbar. That is not a stylistic choice:
a documentation page is not a story, so the preview decorator that stamps
`data-theme` on `<html>` never runs here. Each example therefore carries its
own `data-theme` attribute on a wrapper element — which works exactly as well
there as it does on `<html>` (the mappings are declared on `[data-theme]` as
well as `:root`, so they re-resolve on the wrapper), and is worth knowing if
you ever need two themes on one screen.

## Surfaces

Five steps, and they are M3's: the page is `surface`, then the container
ladder. daisyUI owns the first three; `--surface-3` — row hover, pressed,
selected fill, and a `Dialog`'s panel, which M3 fills with
`surface-container-high` — and `--surface-4` (what `surface-3` becomes inside
`.surface-raised`) are the steps daisyUI's three-tier base system does not
have.

Dark runs `#0f0c1b` → `#151123` → `#1b162c` → `#221c35` → `#28213e`; light
`#fdf7ff` → `#f8f1ff` → `#f2eaff` → `#ede4ff` → `#e8deff`. Both carry the
seed's hue at low chroma — M3's neutral palette — rather than a stock grey.

## Edges

Three tiers, and the name is a deliberate rename from the design document's own
`--border`. daisyUI reserves `--border` for component border *width*, so
reusing the name for a colour would silently overwrite that width value at
`[data-theme]` scope.

`--edge-subtle` is `surface-container-highest`, a hairline inside a surface;
`--edge` is `outline-variant`, M3's divider and outlined-card role.
`--edge-strong` is the one that is not an M3 role, and the reason is a gate:
M3's own control outline, `outline`, measures ΔE2000 18.8 (dark) and 12.5
(light) from the grey `neutral` status hue — under the 30 every surface and
edge must clear — so the generator walks `outline` away from the status hues
to the first tone that clears it. In light that lands almost on
`outline-variant`; the two top steps nearly coincide there, by measurement.
Selection controls (`Checkbox`, `Radio`, `Switch`) take M3's
`on-surface-variant` for their outlines instead, a text-tier colour that also
clears WCAG 1.4.11's 3:1.

<Both>
  <div className="grid grid-cols-3 gap-3">
    <Swatch token="--edge-subtle" className="bg-edge-subtle" note="Internal rules" />
    <Swatch token="--edge" className="bg-edge" note="The default" />
    <Swatch token="--edge-strong" className="bg-edge-strong" note="Emphasis, selected" />
  </div>
</Both>

Borders are the default in this system, not shadows. Only floating layers get a
shadow — `--shadow-popover` (M3 elevation level 2, menus) and `--shadow-dialog`
(level 3, dialogs and snackbars), each M3's two-layer drop shadow plus an
`--edge` hairline, because a black shadow on a near-black page is invisible.
The levels are also exposed as `--md-sys-elevation-level1..3`.

## Text, in three tiers

<Both>
  <div className="flex flex-col gap-1 rounded-box border border-edge bg-surface-1 p-4">
    <p className="text-body text-foreground">
      <code className="font-mono text-caption">--foreground</code> — the value a reader came for.
    </p>
    <p className="text-body text-muted-foreground">
      <code className="font-mono text-caption">--muted-foreground</code> — labels, captions, the
      frame around a value.
    </p>
    <p className="text-body text-subtle-foreground">
      <code className="font-mono text-caption">--subtle-foreground</code> — the dimmest tier;
      metadata a reader skips until they need it.
    </p>
  </div>
</Both>

`--foreground` is an alias onto daisyUI's `--color-base-content`, which is
`on-surface`; `--muted-foreground` is `on-surface-variant`. M3 stops at two
tiers, so `--subtle-foreground` is generated: `on-surface-variant` at the
dimmest tone that still clears AA on every surface step.

**The third tier has a history worth knowing.** `--subtle-foreground` was
`#6b727d`, which fails WCAG AA on every surface in the system — 4.06:1 on the
page background down to 3.40:1 on a hovered row, against the 4.5:1 normal text
requires. It was used in 38 places, every one of them at 11px or 12px, so the
normal-text bar is the right one and none of them qualify for the large-text
exception. It shipped for months.

It was found by the Storybook a11y addon, not by inspection: fourteen weekday
headers of a two-month calendar failing at once is what made a token-level
problem visible. The fix then was the minimum value that cleared AA on the
worst case, and the generator keeps that rule now that the value is derived:
the dimmest tone of `on-surface-variant` that clears 4.5:1 on every surface.
A design system cannot ship text below AA and call the contrast a style
choice.

### One place `--subtle-foreground` is banned outright

**Never put `text-subtle-foreground` on an `InstrumentPanel`.** A shaped
ground breaks the assumption every contrast check in this system rests on —
that a foreground sits on *one* known surface. The panel keeps the damage
countable: its two M3 Expressive shapes are opaque mixes of `primary-container`
into the container (`--instrument-shape`, `--instrument-shape-quiet`), so it
has exactly three grounds, and `contrast.test.ts` measures every tier on each.
On the clover, `--subtle-foreground` falls to **4.05:1 in dark and 4.28:1 in
light**, below the bar, while `--muted-foreground` holds at 5.95:1 and 4.71:1
and every status foreground at least as well. The gate also asserts subtle
still *fails* there, so the ban is lifted the day it stops being needed.

`InstrumentPanel` therefore renders its own caption at `muted` rather than
documenting a rule and trusting every call site to follow it. `StatusPill`
makes the identical move for the identical reason when a loud tint lands under
its label. If you are building a surface on the panel, do the same.

The old aurora mesh (`.aurora-mesh`, which the panel no longer uses) had the
same ban for the same reason: 4.15:1 and 4.25:1 for subtle at the blobs' peak
alpha.

## The state hues

Eight, and their meanings are the subject of the README's hue table. What lives
here is the token shape: each hue declares a foreground, a fill and a border,
and `HUE_CLASSES` maps a hue to the three class names.

Each hue is an M3 **custom colour**: a source hue harmonized toward the seed
(`Blend.harmonize`, at most 15° of rotation) and read off its own tonal
palette, so the full four-role set exists too — `--md-custom-color-<hue>`,
`--md-custom-color-on-<hue>`, `--md-custom-color-<hue>-container` and
`--md-custom-color-on-<hue>-container`. The foreground is the base role.
Three hues depart from the recipe, each with a measurement in the generator:
`neutral` is the scheme's own neutral palette; `parked` is fuchsia and not
harmonized, because violet is the seed's hue; `expired` is separated from
`neutral` by tone, because hue cannot separate two greys. No two hues sit
closer than ΔE2000 13, in either theme.

<Both>
  <div className="flex flex-col gap-2">
    {HUES.map((hue) => (
      <div key={hue} className="flex items-center gap-3">
        <code className="w-20 shrink-0 font-mono text-micro text-muted-foreground">{hue}</code>
        <span
          className={`inline-flex items-center rounded-field border px-2 py-0.5 text-caption ${HUE_CLASSES[hue].fg} ${HUE_CLASSES[hue].bg} ${HUE_CLASSES[hue].border}`}
        >
          loud
        </span>
        <span className={`text-caption ${HUE_CLASSES[hue].fg}`}>quiet</span>
        {isQuietHue(hue) ? (
          <span className="text-micro text-subtle-foreground">no fill, no border</span>
        ) : null}
      </div>
    ))}
  </div>
</Both>

**Two of the eight are quiet.** `neutral` and `success` declare `transparent`
for their own fill and border on purpose, so a screen where most rows succeeded
is a column of glyphs and words rather than a wall of green boxes. That is a
property of the hue vocabulary rather than of either palette, which is why it
holds in both themes and why `isQuietHue` is the single place the fact is
written down.

The consequence is easy to get wrong: a surface that needs a *box* for a quiet
hue must draw ordinary `border-edge`/`bg-surface-2` chrome and keep only the
hue's foreground. Painting the quiet tokens as unconditional chrome produces an
invisible box, and has done so four separate times.

## Scrim and shape

`--scrim` is the overlay wash behind a dialog or drawer: M3's `scrim` role
(black) at 32%, in both themes.

Shape is M3 Expressive's full corner scale, theme-invariant, as
`--md-sys-shape-corner-*`: none 0, extra-small 4, small 8, medium 12, large
16, large-increased 20, extra-large 28, extra-large-increased 32,
extra-extra-large 48, full. Tailwind's `rounded-xs` … `rounded-4xl` are that
scale in order, and daisyUI's three tiers map onto it: `rounded-selector` is
`small` (M3's chip corner), `rounded-field` is `extra-small` (the text-field
corner) and `rounded-box` is `medium` (the card corner). Buttons and
navigation indicators are `full`; dialogs and sheets `extra-large`
(`rounded-sheet`); menus `large`; tables keep square cells.

The checkbox takes `rounded-xs`, and the reason is a fact about how
`border-radius` resolves: **a radius larger than half the box is clamped to
half, and the result is a circle.** 8px is exactly half of the 16px checkbox,
so `small` on a `size-4` box once produced a perfectly round checkbox —
visually identical to a radio button, in a library that ships both.

**The press morph.** Every M3 Expressive button is round at rest and squares
off while held: `--btn-press-radius` is M3's `PressedContainerShape` for the
button's size and density (`small` on `sm`; `small` → `medium` on `md` as the
density goes compact → comfortable). The circular icon button keeps a gentler
tenth of its box, deliberately off-spec: M3's 8px is a quarter of a 32px icon
button, which read as "becoming a square".

**Tables are not pills.** The objection that held the old register to three
steps — "a data table's row and cell chrome would look novelty-bubbly at pill
radius" — still holds, and M3 agrees: tables keep square rows and cells, and
only the containers around them take the scale.

## Density, and the tap-target register

`--density` is the one numeric axis in this file: `0` is compact, `1` is
comfortable, and every size that changes between the two is written as
`calc(<compact value> + var(--density, 0) * <step>)`. It is a number rather
than a keyword so the arithmetic lives in the formula and the axis stays a
single value — a container **style query** (a `style(--density: 1)` predicate
inside a container-query at-rule) would work in Chromium and Safari and not in
Firefox, and a second `data-*` attribute would mean every formula grew a
selector. Spelled in words rather than as the at-rule itself: Tailwind's
`@source "../src"` scanner reads this page, and the bare at-rule token is a
candidate it resolves to a real `container-type: inline-size` utility that
nothing in this library uses.

It is declared once at bare `:root`, so `[data-density="compact"]` needs no
rule of its own, and it inherits — which is the point. Set it on the document
to change the whole app:

```html
<html data-theme="dark" data-density="comfortable">
```

…or on any element to change one subtree, which is what `DetailDrawerContent`
does on a phone-width sheet (`max-md:[--density:1]`) without touching the rest
of the page:

```tsx
<div style={{ "--density": 1 } as CSSProperties}>…</div>
```

An inline style rather than Tailwind's arbitrary-property class, for the same
scanner reason: that class is not one this library uses anywhere — the
component above uses the breakpoint-scoped form — so writing it here would
have the build emit a utility that exists only because a doc page mentioned
it. (The breakpoint-scoped one a paragraph up is fine to write: it is a real
utility `drawer.tsx` actually needs, so the scanner matching it costs
nothing. The trap is a *dead* class name, not any class name.)

Three things read it. `--size-field` (declared on `.input`/`.select`/`.btn`
themselves, never at the theme root — a custom property's `calc()` only
re-evaluates where it is *declared*) carries `Input`, `Select` and `Button`
from 40px to 56px. `.btn-sm`'s own `--size` carries the small button from 32px
to 40px. And `.tap-target` carries everything below.

### `.tap-target` — the 48dp target, and why it is a reservation

Nine icon-only affordances keep their glyph small in both registers, because
that is what the M3 Expressive type and shape register asks for: `Checkbox`,
`Switch`, `CopyButton`, `MaskedValue`'s reveal toggle, the `Dialog`, `Drawer`
and `Toast` close buttons, `DatePicker`'s Clear button and `Calendar`'s
prev/next nav. Their *targets* are what grow at comfortable, and they grow by
**reserving layout space**, not by painting an invisible region over whatever
is next to them.

That is M3's own mechanism rather than a choice made here.
`Modifier.minimumInteractiveComponentSize()` — the modifier `Checkbox`,
`RadioButton`, `Switch` and `IconButton` all call and `Button` does not — is a
`LayoutModifierNode` whose doc reads *"Reserves at least 48.dp in size to
disambiguate touch interactions if the element would measure smaller"* and
*"It only affects layout, to make sure there is adequate space for touch
target expansion"*. Its companion `LocalMinimumInteractiveComponentSize`
spells out what happens without the reservation: *"if the component is placed
near the edge of a layout / near to another component without any padding,
there will not be enough space for an accessible touch target"*. Both quoted
from `compose/material3/material3/src/commonMain/kotlin/androidx/compose/
material3/InteractiveComponentSize.kt` at `androidx-main`
`080d2b3e5326ba80392d93442c4a51a02dc22650`.

So `.tap-target` does two things, and it is the pair that makes the geometry
true rather than merely large:

- it grows the control's own **margin** box to 48px at density 1, so the row
  it sits in grows its pitch with the density. Two adjacent 20px controls end
  up 48px apart centre to centre instead of 18px.
- it covers that reservation with an invisible `::before`, because CSS has no
  equivalent of the platform input-layer expansion M3 relies on: reserved
  margin is not hit-testable on its own, and a pseudo-element *is* part of its
  host for hit-testing — a click landing on it is a click on the button.

The visible box never changes. Neither does the painted state layer: the
reservation is margin, so a `hover:bg-surface-3` disc stays exactly the size
it was, the same way M3 puts `.minimumInteractiveComponentSize()` *before*
`.size(…).background(…)` in `IconButton`'s modifier chain.

**A row that contains one of these controls gets wider at comfortable, and
that is the feature.** `MaskedValue`'s reveal-toggle/`CopyButton` pair is 30px
wide at compact and 102px at comfortable. A target that overlaps its
neighbour is not a target; the width is what buys two of them.

### Using it

Two classes, and five custom properties they read. Every default is what a
control that names nothing gets, so a class on its own is a no-op rather than
a surprise.

- **`.tap-target`** — a control **in normal flow**. Reserves its target as
  margin, then covers it.
- **`.tap-target-anchored`** — a control **absolutely positioned against its
  container's edge**. Covers without reserving, because margin on an
  inset-positioned box moves the box instead of making room around it. The
  container beside it has to reserve the room; see below.
- **`--tap-size`** (default `48px`, i.e. "already big enough, reserve
  nothing") — the control's own resting **border**-box size, for a control
  whose two axes agree.
- **`--tap-w`** / **`--tap-h`** (default: `--tap-size`) — per-axis resting
  border-box size, for a control whose axes differ. `Switch` is the only one
  here: `36px` wide, `20px` tall, so it reserves 6px a side horizontally and
  14px vertically to reach the same 48.
- **`--tap-rest`** (default `0px`) — the control's resting margin, spent only
  while `--density` is `0`, and read by **`.tap-target` only**. `-4px` on the
  in-flow icon buttons, which use the `p-1`-against-a-negative-margin hit-area
  idiom. It is a property of the in-flow variant rather than of that idiom:
  `dialog.tsx`'s close button uses the same idiom with a plain `-m-1` utility
  and no `--tap-rest`, correctly, because `.tap-target-anchored` never writes
  `margin` and so has nothing to hand a resting value to.
- **`--tap-border`** (default `0px`) — the host's own border width. Corrects
  the *cover* and nothing else: an absolutely positioned pseudo-element
  resolves its insets against the host's padding edge rather than its border
  edge, so a bordered host's cover lands 2px short without it. `Checkbox` and
  `Switch` are the two that need it.
- **`--tap-room-top`** / **`-right`** / **`-bottom`** / **`-left`** (default
  `9999px`, i.e. unclamped and therefore symmetric) — `.tap-target-anchored`
  only, and **enforced** rather than merely documented: `.tap-target` declares
  its own four `--tap-cover-*` sides symmetrically, so these inherited
  properties cannot reach an in-flow control. They used to, and it mattered —
  `--tap-room-left: 0px` on `MaskedValue`'s reveal toggle desynced its cover
  from its own margin reservation and produced a 384px² collision with the
  `CopyButton` beside it, through a knob these docs said did not apply.
  A clamp makes no sense in flow anyway: there the reservation *is* the
  containment.

  On the anchored variant, each names how far the cover may reach toward an
  edge the control is anchored to. A clamped side does not shrink the target;
  the opposite side absorbs what it gave up, so the target stays 48px and
  grows inward. Only one call site in this library declares one
  (`DatePicker`'s Clear button, `--tap-room-right: 8px`, which genuinely
  binds); `dialog.tsx` and `calendar.tsx` used to declare non-binding ones
  "in case the offsets change" and no longer do, because a clamp that clamps
  nothing is dormant code and a gate that asserts the cover stays inside the
  panel catches a changed offset whether or not anyone remembered to declare
  a room. All four stay in the API, and all four are exercised — not by a
  call site, but directly against a live element in
  `e2e/tap-targets.spec.ts`'s "the mechanism itself" block, which is what
  makes them a tested surface rather than three unused knobs.

```tsx
// In flow: a 20×20 icon button with the -4px resting margin.
<button className="relative rounded-full p-1 [--tap-rest:-4px] [--tap-size:20px] tap-target">

// Bordered, so the cover needs the correction: a 16px checkbox with a 1px border.
<span className="relative size-4 border tap-target [--tap-size:16px] [--tap-border:1px]">

// Anchored 8px from its container's right edge, so the cover is clamped there
// and grows inward instead.
<button className="absolute top-1/2 right-2 [--tap-room-right:8px] [--tap-size:14px] tap-target-anchored">
```

Three things to know before reaching for either class.

**The host needs its own `position`.** The cover is `position: absolute`, and
neither class sets `position` on its host — deliberately, because several call
sites are already `absolute` via their own anchor offsets and an unlayered
`position: relative` here would outrank a layered `absolute` utility and
silently break them. So an in-flow host needs `relative` in its own class
string. Without it the cover anchors to whatever positioned **ancestor** it
finds — a card, a drawer panel, the page — and becomes a 48px region in
entirely the wrong place rather than nothing at all.

**`--tap-size` is the border box, and getting it wrong is silent.** The class
computes its reservation as `(48px − size) / 2` per side; pass a number that
is not the control's real box and the target is that much off 48 with nothing
to say so. `e2e/geometry.spec.ts`'s D11 block asserts every call site's
computed target lands on 48 — floor *and* ceiling — for exactly this reason.

**`margin` has one writer.** `.tap-target` sets `margin` itself, so a `-m-1`
utility beside it is a second writer of the same property; the resting value
goes in `--tap-rest` instead. The rule lives in `@layer components`, so a
consumer's own `m-*` utility still wins — which also means a consumer's
`m-0` opts that control out of the reservation entirely. That layer is the
whole escape hatch and it is one line, so it is gated: removing only the
`@layer components` wrapper left every test in this package green while
`m-0` silently stopped winning, and `e2e/tap-targets.spec.ts` now asserts
the precedence against a real utility.

### What the compact register does not promise

At density 0 every term above is multiplied by zero, which is what makes
compact byte-identical to the register `vsms` and `vpay` render today — and it
means a compact `CopyButton` is a 20×20 target and `DatePicker`'s Clear button
is 14×14. Both are under WCAG 2.2 SC 2.5.8's own 24 × 24 CSS pixel floor, and
`MaskedValue`'s adjacent pair fails that criterion's Spacing exception too
(two sub-24px targets 18px apart, so the 24px circles intersect). This is
recorded rather than hidden: `e2e/tap-targets.spec.ts` asserts the compact
collision set is *exactly* the one known pair, so a new one fails the build,
and `Docs/Accessibility` carries it as a known gap. Closing it means changing
what compact renders, which is a product decision rather than a token one.

## The aurora ramp

Four stops, and they are the one place in the system where chrome carries hue:
`--aurora-1` through `--aurora-4`, feeding `Skeleton`'s `instrument` drift,
`Card glow` and the `.aurora-mesh` class. `InstrumentPanel` used to paint the
mesh and now paints two `primary-container` shapes instead — chrome in the
seed's own hue family, which needs none of the argument below.

They are drawn from the system's own hues — `progress`, `parked`, a mix of
`parked` and `danger`, and `success` — and bound to them by `color-mix` so they
cannot drift. An earlier version claimed the same thing in a comment while
actually copy-pasting four literals, which is the failure class this changelog
records repeatedly.

What makes them chrome is not a separate hue but the **absence of meaning**: no
status surface reads this ramp, nothing infers state from it, and no caller can
express a state through it. That is the entire safety argument for a coloured
surface in a system whose premise is that colour means something.

Light does not lighten them, and the reason is measured rather than argued.
The obvious move — mix each stop toward white "to free it from a type
constraint", since a glow carries no text — makes it strictly worse: a tint
mixed toward white sits *closer* to a white ground, so every stop loses the
contrast that made it visible and the mesh goes from green-and-lilac to flat
grey. On a light ground, saturation against the ground is the whole budget. So
light keeps the darker, more chromatic values and spends its budget on alpha
instead.

## Switching themes

```tsx
import { ThemeSwitcher, useTheme, THEME_STORAGE_KEY } from "@vaam-apps/ui";
```

<Themed>
  <div className="rounded-box border border-edge bg-surface-1 p-4">
    <ThemeSwitcher persist={false} />
  </div>
</Themed>

That control is live. It writes `data-theme` to this iframe's own `<html>`, so
clicking it re-themes the surrounding documentation chrome rather than the
wrapper it sits in — the wrapper carries its own attribute, which wins for its
subtree. `persist={false}` means nothing is written to storage.

**Three states, not two.** `dark` carries `prefersdark: true`, so this package
already has an opinion about following the operator's OS setting. A plain
light/dark toggle can only represent an *explicit* choice, so the moment one is
wired up, "follow my OS" stops being expressible at all — the toggle has to
start somewhere, and wherever it starts is a decision the operator never made.
A three-state control costs one more option and keeps `prefersdark` meaningful.

`useTheme()` is the headless half, for a settings row, a command-menu action or
a keyboard shortcut:

```tsx
const { preference, resolvedTheme, setPreference } = useTheme();
```

`preference` is what the operator asked for (`"system" | "light" | "dark"`);
`resolvedTheme` is what is actually painted, with `"system"` resolved against
the OS media query. Render the first to decide which control is checked, the
second to write "currently dark" copy. `setThemePreference` is the same path
outside React.

The preference persists to `localStorage` under `THEME_STORAGE_KEY`
(`"vaam-ui:theme"`), namespaced so it cannot collide with a consuming app's
other keys. Every read and write is wrapped in `try`/`catch` — Safari's private
windows throw on `setItem`, and some webviews and org policies block storage
entirely. Losing persistence for a session is an acceptable degradation;
throwing out of a click handler is not.

`persist={false}` — used by the switcher above, and by this package's own
stories — re-themes the document without writing anything. A switcher mounted
in a story without it writes into Storybook's own `localStorage`, where the
value outlives the story and silently overrides the theme toolbar on a later
load.

For the first-paint flash and the inline script that prevents it, see
[Installation](?path=/docs/docs-installation--docs).

## The contrast gate

`src/lib/contrast.test.ts` is the reason the generated palette is
trustworthy, and it is worth reading before changing any colour here.

**What it checks.** It parses `theme.css` itself — not a duplicated table of
values, and not the generator's output — resolving every `var()` chain the way
the cascade does for `<html data-theme="…">`, and asserts:

- The theme **roster**, by name: exactly `dark` and `light`.
- That each theme declares all five surfaces, all eight status foregrounds, and
  all three text tiers **by name**.
- Every foreground against every surface, in every theme, at the 4.5:1 AA bar
  for normal text.
- Every **loud** status foreground against its own `--state-*-bg` tint
  composited onto each surface.

The roster and by-name assertions are not belt-and-braces. An earlier version
asserted a floor on the number of generated cases instead, and stayed green
with the entire light theme deleted — one theme still produced 44 cases,
comfortably over the old floor. A floor on cases cannot catch a missing theme,
because the remaining theme already clears it. Separately, the parser only
keeps a token that resolves to `#rrggbb`: rewrite a tier as `rgb(91 99 113)`
— a form this very stylesheet uses elsewhere — or point its `var()` at a role
that does not exist, and it drops silently out of the case list with every
guard still green. The one token whose historical failure gave the file its
reason to exist is the one that could have vanished unnoticed.

**Why it came first.** `theme-tokens.test.ts` asserts a token is *declared*. It
cannot assert the value is *legible*, and that gap had already cost a real
accessibility failure. Adding a light theme multiplied the risk by eight: every
status foreground is a 300-level tint chosen for roughly 11:1 against
near-black, and measured against white all eight landed between **1.4:1 and
2.6:1** — every one below AA. A light palette picked by eye would have shipped
a status vocabulary nobody could read, and nothing in the build would have said
a word.

So the gate was written **before** the colours, and it still outranks them.
The palette is generated now, and where Material's recipe would fail the gate
the generator departs from the recipe: M3's custom-colour base tone in light
is 40, and a loud `progress` label at 40 measured 4.46:1 on the top container
step, so the light status foregrounds sit at 38 (worst case 4.80:1).

**The composited case it caught.** The file originally measured bare surfaces
only, and said so in its own header: extending it to composited grounds "is
worth doing and is not done here". It was worth doing, and the block that does
it found two loud pills below AA on `--surface-3`, the row-hover fill —
`expired` at **4.27:1** and `danger` at **4.36:1**. Both cleared the bar on a
bare surface, both were invisible to the flat check, and both were invisible to
axe as well, because no story renders a loud pill on a hovered row. The
original limitation note is kept in the file as history rather than deleted,
because the gap it describes is the reason the block exists.

The hand-picked palette of the time was fixed by darkening those two; the
generated palette is held to the same composited check from the start.

The asymmetry is worth internalising if you touch either palette: in dark, a
translucent tint *lightens* the ground under an already-light foreground and
the ratios stay comfortable. In light it *darkens* the ground under an
already-dark foreground. The same palette logic does not transfer between the
two.

## Changing a colour

1. A generated colour (any `--md-sys-color-*`, `--md-custom-color-*`,
   `--state-*`, `--subtle-foreground`, `--edge-strong`) changes in
   `scripts/generate-md3-colors.ts` — the seed, a status source, a tone — and
   then `pnpm generate:colors`. A mapping (`--surface-3`, `--edge`, the
   daisyUI keys) changes in `theme.css`.
2. Run `pnpm test`. `contrast.test.ts` will tell you the measured ratio and
   which surface it failed on; `hct-neutrals.test.ts` will tell you if a hue
   pair, or `primary` and a hue, fell under ΔE2000 13, or the CSS drifted
   from the generator; `theme-tokens.test.ts` will tell you if a component
   references something you removed.
3. If you are adding a hue or a tier, it lands in **both** themes through the
   generator. The roster checks are what turn a half-finished change into a
   failing build.
4. Do not relax a gate. Move the tone, or harmonize a hue less — the
   generator's comments record each time that was the answer.
